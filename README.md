# A Smart Home That Learns Its Own Automations

Code and experiments for the article (in preparation) on an MQTT smart home that learns its
residents' habits. It builds on two articles:

- **Starting system:** Özdoğan, E.; Daş, R. IoT based a Smart Home Automation System Design: Simulation
  Case. *Balkan J. Electr. Comput. Eng.* **2021**, 9, 297–303. https://doi.org/10.17694/bajece.918826.
  Its MQTT home and three rule scenarios are rebuilt in Cisco Packet Tracer and in Python over a real
  Mosquitto broker.
- **Followed article:** Gad, M.M.; Gad, W.; Abdelkader, T.; Naik, K. Personalized Smart Home Automation Using
  Machine Learning: Predicting User Activities. *Sensors* **2025**, 25, 6082.
  https://doi.org/10.3390/s25196082. Its method is replicated on its own data (CASAS), tested with a
  time-ordered split, and compared with ours in both directions.

The home finds habits by counting (routines and quiet windows), offers them as suggestions the user must
approve, and lets each device limit what automation may do to it. A random forest checks the suggestions on
unseen days and guards standby cuts; a standby-cut rule that is wrong three times switches itself off. Smart
start runs a loaded dishwasher or washing machine before the user's deadline, when the most solar energy is
expected to be left after the rest of the house's usual load.

## Main results and the scripts that produce them

| Result | Script |
| --- | --- |
| Habit prediction on later weeks: the random forest beats the hour-of-week baseline on REFIT (median F1 0.238 vs 0.169, 123 tasks, p = 6.4e-15), UK-DALE and CASAS | `eval_refit.py` (REFIT, UK-DALE); `kaggle/gad_comparison.ipynb` (CASAS) |
| GRU and CNN-GRU as habit models: better than the baseline, worse than the forest | `eval_habit_networks.py` (`kaggle/habit_networks*.ipynb`) |
| Gad et al. replicated: accuracy 0.846 with their random split (paper 0.915), 0.512 with a time split; "same activity as the previous labelled interval" then wins in all 21 homes | `eval_gad.py` (`kaggle/gad_comparison.ipynb`) |
| Every model tested both ways scores higher with a random split than with a time split | `eval_split_effect.py` (`kaggle/split_networks.ipynb`) |
| Smart start: solar share of machine energy 16.8% → 53.6% (REFIT, 19 homes) and 24.1% → 70.4% (UK-DALE) with a perfect solar forecast, an upper bound | `eval_suggestions.py smart` |
| Smart start with realistic forecasts: 41.3–43.0% (REFIT) and 51.7–54.3% (UK-DALE); a perfect load forecast would add at most 6.6 points | `eval_smart_start_forecasts.py` |
| Standby cuts with the three-strike rule: median 5.0% (REFIT) and 3.6% (UK-DALE) of cut nights interrupted, about 9 and 23 kWh/year per home | `eval_suggestions.py cuts` |
| MQTT traffic of one home and broker load | `measure_mqtt.py` |
| Hour-ahead load forecasting of single homes (Yaprakdal 2023, 2024): no published model beats persistence significantly; trained with absolute error, gradient boosting beats persistence and the networks | `eval_forecast.py`, `eval_forecast_habits.py` (`kaggle/capstone_kaggle.ipynb`, `kaggle/forecast_networks.ipynb`) |
| Homes never seen in training; REFIT → UK-DALE external test | `eval_houses.py`, `eval_external.py` |
| Datasets described | `analyze_data.py`, `analyze_casas.py` |

All scripts are in `scripts/` and write their tables to `data/results/` (`data/results/ukdale/`,
`data/results/casas/`).

## Layout

| Folder | What it holds |
| --- | --- |
| `home/` | The simulated home: message format, MQTT bus, devices with control types, rule engine with the three-strike rule, smart-start scheduler, SQLite event log, phone notifications, the starting article's three scenarios |
| `habits/` | Habit learning. System: power traces to appliance uses, routines and quiet windows, suggestions with energy estimates, the random forest that checks suggestions and guards standby cuts (`forest.py`). Research: hourly dataset, features, baseline, forest, GRU / CNN-GRU, Gad et al.'s method (`gad.py`). Loaders for REFIT, UK-DALE and CASAS |
| `energy/` | Hour-ahead load forecasting following Yaprakdal (2023, 2024) |
| `dashboard/` | FastAPI web dashboard: devices, energy, smart start, suggestions to accept or reject |
| `scripts/` | Data preparation (`prepare_*`), one script per experiment (`eval_*`), demos, Kaggle packaging |
| `kaggle/` | The notebooks that ran the long experiments (generated by `scripts/make_notebook.py`) |
| `tests/` | `pytest` suite (the broker test runs only when Mosquitto is up) |
| `docs/` | Design diagrams and figures, the Packet Tracer rebuild (`packet_tracer.md`, `article-home.pkt`) |

## Setup

Python 3.14 (Windows commands shown; on Linux or macOS use `.venv/bin/python`):

```powershell
py -3.14 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
winget install EclipseFoundation.Mosquitto   # MQTT broker on 127.0.0.1:1883 (for the demos)
```

The networks need PyTorch (`pip install torch --index-url https://download.pytorch.org/whl/cpu` is enough
outside Kaggle).

```powershell
.venv\Scripts\python.exe -m pytest                 # all tests
.venv\Scripts\python.exe scripts\demo_article.py   # the starting article's 3 scenarios over Mosquitto
.venv\Scripts\python.exe scripts\run_dashboard.py  # dashboard on http://127.0.0.1:8000
```

With REFIT prepared, the dashboard replays a real household (REFIT house 6): suggestions are learned from
its first 80% of days, checked by the random forest, and its last 20% is replayed with that day's real sun.
Without the data it uses a small synthetic household. Optional phone notifications go through
[ntfy](https://ntfy.sh): set `NTFY_URL` to a topic of your own.

## Data

The datasets are not in this repository; all are public under CC BY 4.0.

| Dataset | Source | Preparation |
| --- | --- | --- |
| REFIT (cleaned), 20 homes near Loughborough | Murray et al., *Sci. Data* 2017, https://doi.org/10.1038/sdata.2016.122; data: https://pureportal.strath.ac.uk/en/datasets/refit-electrical-load-measurements-cleaned/ | Put `CLEAN_REFIT_081116.7z` (extracted), `CLEAN_READ_ME_081116.txt` and `MetaData_Tables.xlsx` in `data/raw/refit/`, then `scripts/prepare_refit.py` |
| UK-DALE, 5 London homes | Kelly & Knottenbelt, *Sci. Data* 2015, https://doi.org/10.1038/sdata.2015.7 | `scripts/prepare_ukdale.py` (run on Kaggle, 3.6 GB) |
| CASAS, the 21 single-resident homes of Gad et al. | Cook et al., *Computer* 2013, https://doi.org/10.1109/MC.2012.328; data: https://zenodo.org/records/15708568 (`labeled_data.zip`) | `scripts/prepare_casas.py` (run on Kaggle) |
| Solar output and weather | PVGIS 5.3, European Commission JRC, https://re.jrc.ec.europa.eu/pvg_tools/en/ | Fetched on first use, cached in `data/raw/pvgis/` |

Select the dataset with `CAPSTONE_DATASET=ukdale` or `CAPSTONE_DATASET=casas` (REFIT is the default).

Long runs went to Kaggle: `scripts/make_bundle.py` packs the code and prepared REFIT tables into
`data/bundle/capstone-bundle.zip`, which is uploaded as a private dataset; then import a notebook from
`kaggle/`. Results computed on Kaggle and on a laptop can differ slightly because of library versions;
every comparison is made within one environment.
